[로봇 하드웨어] 시리즈 가이드라인

하드웨어 관점에서 본 Physical AI — 다관절 로봇 하드웨어 시리즈의 집필·편집 기준 새 글을 쓰거나 기존 글을 고칠 때 이 문서를 기준으로 삼는다.

1. 시리즈의 목적
핵심 질문

하드웨어의 어떤 물리적 특성이 "모델이 가정한 로봇"과 "실제 로봇"을 다르게 만드는가? 그리고 그 차이를 어떻게 다룰 것인가?

모든 글은 이 질문에 답한다. 하드웨어 지식은 목적이 아니라 수단이며, 위 질문에 답하는 데 필요한 만큼만 설명한다.

독자
주 독자: 강화학습, 모방 학습, VLA 등으로 실제 로봇을 다루는 AI·로봇 학습 연구자. 하드웨어 배경이 깊지 않다고 가정한다.
부 독자: 로봇 하드웨어 엔지니어. 익숙한 하드웨어 특성이 학습 기반 제어에서 어떤 문제가 되는지라는 새로운 관점을 제공한다.
하지 않는 것
부품 카탈로그나 교과서식 설명(구조 → 원리 → 장점 → 단점 나열)
설계 노하우 자체를 목적으로 한 전문지식 나열
특정 제품 리뷰나 구매 가이드
2. 분석 틀
차이의 세 가지 형태 — 한 번만 소개하고 태그로 쓰지 않는다

하드웨어가 만드는 차이는 대략 세 가지 형태로 나타난다.

시뮬레이터에 아예 없는 특성 → 모델에 추가해야 한다
모델에 있지만 값이 틀린 특성 → 식별해야 한다
측정값과 추정치에 섞이는 오차 → 걸러내거나 센서를 바꾸거나 관측에 넣어야 한다

이 분류는 1편과 2편 도입에서 한 번 소개한다. 이후 글에서는 현상마다 "분류: 모델 오차" 같은 라벨을 붙이지 않는다. 경계가 깔끔하지 않고, 라벨이 붙으면 글이 체크리스트처럼 읽히기 때문이다. 대신 각 현상을 **"그래서 어떻게 다룰 것인가"**로 마무리하면 분류는 저절로 드러난다.

숨은 상태 (Hidden State) — 시리즈 후반을 관통하는 축

실제 액추에이터의 출력은 시뮬레이터나 정책이 보지 못하는 상태 변수에 의존한다. "이 오차는 어떤 상태에 묶여 있는가"를 밝히는 것이 Gaussian noise 모델과 이 시리즈의 설명을 구분하는 핵심이다.

4. 글의 구조
본편 템플릿
도입: 관측 가능한 실패 장면 구체적인 증상으로 시작한다. 예: "시뮬레이터에서는 손으로 밀면 밀리던 팔이 실제로는 꿈쩍도 하지 않다가, 더 세게 밀면 툭 튀어나갑니다."
모델이 가정하는 것 시뮬레이터·제어기가 이 부분을 보통 어떻게 다루는지 한두 문장으로 밝힌다.
현상별 블록 (현상마다 반복)
물리적 원인: 현상을 설명하는 데 필요한 최소한의 식과 물리
어떻게 드러나는가: 정책, 제어, 데이터에서 실제로 보이는 증상. 숨은 상태가 있으면 밝힌다
어떻게 재는가: 측정하거나 분리하는 방법
어떻게 다루는가: 모델에 추가, 식별, 관측에 넣기, 하드웨어 변경 등
정리 표 | 요소 | 모델의 흔한 가정 | 실제 | 생기는 문제 | 형식. 다른 글이 본거지인 행에는 링크를 단다.

5. 문체
기본
합니다체를 쓴다.
문단은 3–4문장 안팎으로 유지하고, 한 문장에는 주장 하나만 담는다.
결론을 먼저 쓰고 근거를 뒤에 쓴다.
용어
처음 나올 때 한국어 용어 뒤 괄호에 영어를 쓴다: 역구동성(Backdrivability). 이후에는 한쪽만 쓴다.
업계에서 영어로 굳은 용어(policy, current loop, derating 등)는 영어로 써도 되며, 한 글 안에서는 표기를 통일한다.
한국어 신조어보다 영어 기술 용어를 우선한다. 예: 반사 관성·겉보기 관성 대신 reflected inertia.
"BLDC"는 시장 관례대로 쓰되, 02에서 한 번 "엄밀히는 PMSM 계열"임을 밝힌다.
소제목
소제목은 문장으로 쓰지 않고 명사구로 쓴다. "~다", "~니다"로 끝나는 서술형과 "~인가", "~나" 같은 질문형을 모두 피한다. 예: "마찰은 상수가 아니다" → "속도·부하·온도에 따른 마찰 변화", "감속비는 무엇을 위한 설계 변수인가" → "설계 변수로서의 감속비".
콜론 뒤 부제도 명사구로 쓴다. 예: "대가 3: 감속기의 비틀림 강성".
섹션의 주장은 소제목이 아니라 섹션 첫 문장에 쓴다.
단서와 단정
가정은 섹션 시작에서 한 번 밝힌다. 문장마다 "다만 ~일 수 있습니다"를 붙이지 않는다.
일반화할 수 없는 주장에는 조건을 붙이고, 확실한 물리 법칙은 단정한다.
과장을 피한다. "파손되지 않는다", "불가능하다", "zero backlash" 같은 단정 대신 조건과 정도를 쓴다.
수치
물리 상수와 근사값에는 출처를 단다.
설명용으로 만든 값은 예시값임을 밝힌다.
같은 현상의 예시 조건은 시리즈 전체에서 맞춘다.
reflected inertia: J_m = 1×10⁻⁵ kg·m², N = 100, J_L ≈ 0.09 kg·m² (02, 03)
발열: 25 °C → 75 °C (06)

7. 마크다운과 렌더링 규칙
디스플레이 수식은 $$ ... $$로 감싸고, 여러 줄이면 aligned 환경을 쓴다. =나 -만 있는 줄이 생기면 setext 헤딩으로 해석되어 수식이 깨진다.
인라인 수식은 $...$로 쓴다. 백틱 코드(i_q)로 쓰지 않는다.
물결표는 취소선으로 해석될 수 있으므로 범위에는 –를 쓰거나 \~로 이스케이프한다. 예: 30–50%, 30:1–160:1.
굵은 글씨는 한국어 용어에만 걸고 괄호는 밖에 둔다: **역구동성**(Backdrivability)을.
이미지는 파일이 실제로 있는지 확인하고, 캡션만 남은 이미지를 두지 않는다. 모든 이미지에 alt 텍스트를 단다.
표는 항목 × 속성 비교에만 쓴다.
인용은 기존 형식을 따른다: 본문 [1](#ref-1), 목록 <span id="ref-1"></span> + [1] ....
8. 링크, 제목, URL
제목 형식: [로봇 하드웨어 NN] - 액추에이터 (n): 주제. 서브포스트는 [로봇 하드웨어 NN-k] - 주제.
description(부제)은 내용을 설명하는 한 줄로 쓴다. "Physical AI 관점에서 본 다관절 로봇 하드웨어 - X" 형식은 쓰지 않는다.
"다음 포스트" 링크의 제목은 대상 글의 title과 글자 하나까지 같게 쓴다.
front matter의 series_order, series_label을 로드맵 번호와 맞춘다.
KR과 EN은 같은 구조, 같은 그림, 같은 참고문헌 번호를 유지한다. 한쪽을 고치면 다른 쪽도 고친다.
번호가 바뀌어 URL이 겹치는 글은 번호 대신 내용 기반 permalink를 쓰고, 옛 URL은 새 글로 리디렉트한다 (CLAUDE.md의 URL 계획 참조).
9. 참고문헌과 이미지
형식은 IEEE 스타일을 따른다: 저자, “제목,” 학술지, 권, 호, 쪽, 연도. DOI 링크를 단다.
번호는 본문에 처음 나오는 순서대로 매긴다.
본문에서 인용하지 않는 항목은 목록에 두지 않는다.
인용 내용과 출처가 실제로 일치하는지 확인한다.
이미지는 라이선스가 명확한 것(CC, 퍼블릭 도메인, 직접 제작)만 쓰고, 라이선스와 출처를 표기한다.
개념 모델 그림은 직접 만들고, 캡션에 사용한 파라미터를 적는다.
직접 만든 정적 플롯(생성한 PNG·SVG 그래프)은 쓰지 않는다. 계산 결과를 보여 줄 때는 인터랙티브 데모로 만들고, 데모 설명에 모델과 파라미터를 적는다.
10. 발행 전 체크리스트
 도입이 구체적인 실패 장면으로 시작하는가
 각 현상이 "어떻게 드러나는가 → 어떻게 재는가 → 어떻게 다루는가"로 마무리되는가
 현상마다 분류 라벨을 붙이지 않았는가
 소제목이 모두 명사구인가 (서술형·질문형 없음)
 구조화된 오차라면 어떤 숨은 상태에 묶여 있는지 밝혔는가
 다른 글이 본거지인 개념을 깊이 다루지 않고 링크했는가
 정리 표가 있고, 다른 글이 본거지인 행에 링크가 있는가
 기호가 6장의 규칙과 일치하는가
 수치에 출처가 있거나 예시값임을 밝혔고, 예시 조건이 시리즈와 일치하는가
 수식, 물결표, 굵은 글씨가 로컬 빌드에서 제대로 렌더링되는가
 이미지 파일이 모두 있고 라이선스가 표기되었는가
 참고문헌에 미인용 항목이 없고 번호가 등장 순서와 맞는가
 "다음 포스트" 링크의 URL과 제목이 대상 글과 일치하는가
 KR과 EN이 같은 구조로 갱신되었는가
