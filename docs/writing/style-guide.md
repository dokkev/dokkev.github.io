# Writing Style Guide

이 저장소의 블로그, 프로젝트 소개, 연구 설명, 문서와 웹사이트 문구에 적용하는 공통 글쓰기 기준입니다. 한국어와 영어 모두에 적용합니다. 개별 글을 쓸 때 독자, 목적, 발행 형식을 먼저 정하고, 해당 작업에서 명시한 요구사항을 우선합니다.

## 1. 핵심 원칙

**이 문장을 지우면 독자가 잃는 정보가 있는가? 없으면 지웁니다.** AI slop은 정보 없이 형식만 남은 문장입니다. 표현을 다른 유행어로 바꾸기보다 빠진 사실을 채우거나 문장을 삭제합니다.

1. **구체성이 곧 문체입니다.** 형용사 대신 대상, 동작, 수치와 조건을 씁니다. 수치가 없으면 실제로 확인한 구조나 동작을 설명합니다.
2. **주장은 한 번, 근거와 함께 씁니다.** 도입·본문·결론에서 같은 주장을 반복하지 않습니다.
3. **독자가 아는 것은 생략합니다.** 독자를 먼저 정하고, 그 독자가 현재 설명을 이해하는 데 필요한 배경만 제공합니다.
4. **구조는 내용에서 나옵니다.** 항목 수, 대구, 소제목과 고정 목차를 먼저 정해 내용을 끼워 넣지 않습니다.

구체적으로 쓰기 위해 숫자, 실험 조건, 경험담을 만들어서는 안 됩니다. 자료가 없으면 범위를 줄이거나 확인이 필요한 내용을 표시합니다.

## 2. 단어: 평가를 사실로 바꿉니다

다음 표현은 구체적인 정보가 빠졌는지 점검하는 신호입니다. 전문 용어로 정확한 의미가 있는 경우에도 이 글에서 어떤 의미와 조건으로 쓰는지 밝힙니다.

| 점검할 표현                                      | 편집 방향                                                                          |
| ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `delve`, `dive into`, `explore`                  | 실제 동작인 `measure`, `compare`, `describe` 등을 쓰거나 바로 본론으로 들어갑니다. |
| `leverage`, `utilize`, `harness`                 | 같은 뜻이면 `use`를 씁니다.                                                        |
| `robust`, `powerful`, `seamless`, `cutting-edge` | 어떤 조건에서 무엇이 동작하거나 유지되는지 씁니다.                                 |
| `crucial`, `pivotal`, `plays a key role`         | 해당 요소가 바꾸는 결과나 없을 때 발생하는 문제를 설명합니다.                      |
| `landscape`, `realm`, `ecosystem`, `journey`     | 실제 대상인 분야, 라이브러리, 프로젝트 등의 이름을 씁니다.                         |
| `unlock`, `elevate`, `empower`                   | 새로 가능해진 구체적인 동작을 씁니다.                                              |
| `It's worth noting that`, `Importantly`          | 앞부분을 지우고 사실을 바로 씁니다.                                                |
| `In today's fast-paced world`와 비슷한 시대 배경 | 글의 판단에 필요한 정보가 없으면 삭제합니다.                                       |
| `simply`, `just`, `easily`                       | 삭제하거나 실제 절차와 전제조건을 설명합니다.                                      |
| `comprehensive`, `holistic`                      | 포함하는 범위와 제외하는 범위를 구체적으로 씁니다.                                 |

한국어의 `매우 중요하다`, `획기적이다`, `손쉽게`, `강력하다`, `완벽하게 통합한다`도 같은 기준으로 점검합니다. 번역 과정에서 영어의 과장만 한국어로 옮기지 않습니다.

## 3. 문장: 행위와 조건을 직접 씁니다

### 불필요한 대조를 만들지 않습니다

독자가 제기하지 않은 주장을 먼저 부정하는 `Not X, but Y`, “단순한 X가 아니라 Y” 구조를 반복하지 않습니다. 설명하려는 동작과 차이를 직접 씁니다. 실제 오해를 바로잡는 글에서는 오해의 내용과 바로잡는 근거를 명확히 제시합니다.

> The gripper switches between pinch and power grasp with one motor.

이 문장은 문체 예시이며 특정 장치에 대한 사실 보고가 아닙니다.

### 나열은 실제 항목 수를 따릅니다

`fast, flexible, and scalable`처럼 리듬을 위해 세 항목을 묶지 않습니다. 각각 독립적인 정보와 근거가 있을 때만 나열합니다. 하나만 확인했다면 하나만 씁니다.

### 문장부호로 반전을 연출하지 않습니다

Em dash는 문단당 하나 이하로 제한하고 대부분 쉼표나 마침표로 바꿉니다. `The result?`, `Here's the thing:`, `Why does this matter?`처럼 답을 늦추는 장치는 지우고 결과나 이유를 바로 씁니다.

### 불확실성은 한 번, 이유와 함께 씁니다

`may`, `potentially`, `arguably`를 겹치지 않습니다. 알려진 범위와 확인하지 못한 범위를 구체적으로 적습니다. 관측한 결과와 그 원인에 대한 추정을 구별하며, 인과관계를 확인하지 못했다면 원인으로 단정하지 않습니다.

### 주체와 동사를 드러냅니다

명사화와 수동태가 주체를 가리면 행위자를 주어로 세웁니다. `An optimization was performed`보다 `We optimized the trajectory`처럼 누가 무엇을 했는지 씁니다. 실제 수행자가 확인되지 않은 작업을 `we`의 경험담으로 만들지 않습니다.

### 한 문장에 한 가지 생각을 둡니다

영어 문장이 25단어를 넘으면 분리할 지점을 찾습니다. 한국어도 여러 원인과 결과를 한 문장에 겹치지 않습니다. 단어 수를 줄이는 과정에서 필요한 조건을 삭제하지 않습니다. 약어는 처음에 한 번 풀고, 같은 대상을 문장마다 다른 이름으로 바꾸지 않습니다.

## 4. 문단과 글의 전개

**문단의 첫 문장에 요점을 둡니다.** 나머지 문장은 이유, 근거, 조건이나 결과를 설명합니다. 문단마다 하나의 중심 생각을 두고, 한 문장짜리 강조 문단을 연속해서 배치하지 않습니다.

도입부는 독자가 이 글을 읽을 이유가 되는 문제, 결과 또는 구체적인 혼동에서 시작합니다. 분야의 중요성, 역사, `In this post, we'll explore` 같은 안내로 지면을 채우지 않습니다. 배경은 현재 질문을 이해하는 데 필요한 위치에서 설명합니다.

인과관계와 trade-off는 연결된 문장으로 씁니다. 불릿은 사양, 비교 대상처럼 병렬인 항목에 사용하고, 설치 절차처럼 순서가 있으면 번호 목록을 사용합니다. 설명을 불릿으로 나누면서 `because`, `so`, `but`에 해당하는 연결을 지우지 않습니다.

> Routing cables to remote motors reduced the finger's inertia, but added friction that varied with joint angle. The model omitted that friction and no longer matched the measured response.

이 문단도 설명용 예시입니다. 실제 글에서는 해당 구조, 마찰의 관측 근거와 모델 비교 결과가 있을 때만 이처럼 씁니다.

소제목은 아래 문단이 무엇을 설명하는지 드러내야 합니다. `Overview`, `Key insights`, `Conclusion`을 습관적으로 붙이지 않으며, 글마다 같은 수의 절과 같은 결론 구조를 강제하지 않습니다.

마지막 문단에서 본문을 다시 요약하거나 미래에 대한 기대를 덧붙이지 않습니다. 남은 한계, 다음 확인, 독자가 적용할 수 있는 구체적인 조치로 끝내거나 마지막 결과에서 멈춥니다. 글의 질문에 대한 답이 마지막까지 미뤄질 필요는 없습니다.

## 5. 기술적 주장은 검증 가능한 형태로 씁니다

### 수치에는 조건과 비교 기준을 붙입니다

성능 숫자에는 그 숫자를 해석하는 데 필요한 하드웨어, 데이터·작업 조건, 비교 대상, 반복 횟수와 통계량을 적습니다. 측정 위치, 단위, 평균·중앙값·최댓값을 구별합니다. 적용되지 않는 항목을 형식적으로 채우지는 않습니다.

다음은 **가상의 문체 예시**이며 실제 프로젝트 결과로 인용하면 안 됩니다.

> On an RTX 4090, the planner took 12 ms per query, compared with 38 ms for RRT* (median over 500 queries).

`3× faster`처럼 비율만 적기보다 원래 값과 비교 조건을 제공합니다. 성공률의 차이는 percentage points와 상대 개선율을 구별합니다. 데이터가 없으면 그럴듯한 숫자로 문장을 완성하지 않습니다.

### 평가 용어를 비교 결과로 바꿉니다

`state-of-the-art`라고 쓰려면 비교한 방법, 벤치마크, 평가 지표와 조건을 제시합니다. `robust`라고 쓰려면 어떤 외란이나 조건 변화에서 어떤 결과를 유지했는지 적습니다. 성능 개선과 이를 유발했다고 추정하는 메커니즘을 같은 수준의 확정적 주장으로 쓰지 않습니다.

### 실패와 적용 한계를 씁니다

성능을 주장하는 글에서는 관측한 실패 조건이나 확인하지 못한 범위를 밝힙니다. 개념 정의나 설치 안내에 가상의 실패 사례를 억지로 추가하지 않습니다. 한계는 해당 결과의 적용 범위를 판단할 수 있는 수준으로 씁니다.

문서에 정의된 동작, 실제 측정, 계산 예제, 시뮬레이션과 원인 추정을 구별합니다. 실행 기록이 없는 예제를 “테스트했다”라고 쓰지 않습니다. 시뮬레이션 결과를 물리 실험으로, 정적 검사 결과를 런타임 검증으로 바꿔 부르지 않습니다.

## 6. 코드·수식·그림·데모

코드 앞에는 목적을 한 줄로 설명합니다. 코드 자체를 `simple yet powerful`, `elegant`라고 평가하지 않습니다. 코드 뒤에는 왜 특정 값을 쓰는지, 어떤 출력으로 결과를 판단하는지처럼 코드만으로 알 수 없는 내용을 적습니다. 각 줄을 다시 풀어 쓰지는 않습니다.

코드 블록에는 코드, 명령, 출력, 패킷 형식처럼 고정폭 표기가 필요한 내용을 넣습니다. 일반적인 주장이나 강조 문장을 코드 블록으로 감싸지 않습니다. 명령과 출력 예시를 구별하고, 재현에 필요한 버전과 실행 조건을 제공합니다.

수식은 관계를 압축할 때 사용합니다. 기호, 단위, 좌표계나 측정 위치, 가정과 생략한 항을 필요한 만큼 정의합니다. 수식 뒤에는 그 관계가 현재 문제에서 무엇을 의미하는지 설명합니다.

그림과 표는 비교 기준과 조건이 대응하도록 만듭니다. 그래프에는 축·단위·범례·조건을 표시하고, 캡션에는 읽어야 할 관계를 적습니다. 외부 자료에는 출처와 재사용 조건을 기록합니다.

인터랙티브 데모를 넣더라도 본문에서 모델, 기본 조건, 대표 결과와 해석을 읽을 수 있어야 합니다. 계산 예제와 실측을 구분하고, 실제 기록이 없는 노이즈나 로그로 측정 결과처럼 꾸미지 않습니다.

## 7. 근거와 용어를 관리합니다

핵심 기술 설명에는 표준, 공식 문서, 제조사 자료, 논문 또는 해당 버전의 소스처럼 주장에 맞는 근거를 사용합니다. 관련 문장과 그림 가까이에 출처를 두고, 쓰지 않은 자료를 참고문헌에 채우지 않습니다.

같은 대상에는 같은 이름을 씁니다. 손을 `hand`, `gripper`, `end-effector`, `device`로 번갈아 부르면서 서로 다른 대상처럼 보이게 하지 않습니다. 실제로 구분해야 하는 대상이면 처음에 관계를 정의합니다.

기존 원고의 수치, 경험담과 출처도 새 원고에 옮기기 전에 확인합니다. 용어의 범위나 제품·API 지원처럼 달라질 수 있는 정보는 발행 시점에 다시 확인합니다.

## 8. 퇴고 체크리스트

- [ ] 독자가 누구이며 무엇을 얻어야 하는지 정했는가?
- [ ] 첫 문장이 구체적인 문제, 결과 또는 혼동을 제시하는가?
- [ ] 평가 형용사와 유행어를 삭제하거나 확인 가능한 사실로 바꿨는가?
- [ ] 불필요한 대조, 극적인 질문, 리듬용 나열을 지웠는가?
- [ ] Em dash가 문단당 하나 이하인가?
- [ ] 영어 25단어를 넘는 문장과 여러 생각을 겹친 문장을 나누었는가?
- [ ] 문단 첫 문장에 요점이 있고 나머지에 근거가 연결되는가?
- [ ] 불릿으로 나누면서 인과관계와 trade-off를 잃지 않았는가?
- [ ] 성능 숫자에 필요한 단위, 조건, 비교 기준과 통계량이 있는가?
- [ ] 성능 주장의 실패 조건이나 미검증 범위를 밝혔는가?
- [ ] 같은 대상을 같은 이름으로 부르고 약어를 처음에 정의했는가?
- [ ] 코드 뒤에 줄별 재설명 대신 필요한 해석을 붙였는가?
- [ ] 본문 없이 그림이나 데모만 보아야 알 수 있는 핵심 설명이 남아 있지 않은가?
- [ ] 마지막 문단의 재요약과 상투적인 기대를 지웠는가?
- [ ] 각 문장을 지워 보며, 독자가 잃는 정보가 없는 문장을 삭제했는가?
